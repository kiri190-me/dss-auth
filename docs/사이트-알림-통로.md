# 사이트가 포털에 「이 사람의 합쳐진 알림」을 묻는 통로

각 사이트의 **서버**(layout)가 포털을 한 번 부른다. 브라우저가 부르는 길이
아니다 — 포털 세션 쿠키가 없는 곳에서 부르기 때문에 자격은 **그 사이트의
client_secret** 이다.

```
각 사이트의 서버 ──(Basic client_id:client_secret)──▶ 포털 ──(서명 토큰)──▶ 다른 시스템들
```

## 부르는 법

```
POST {포털}/api/integration/notifications
Authorization: Basic base64(urlencode(client_id) + ":" + urlencode(client_secret))
Content-Type: application/x-www-form-urlencoded

sub=<포털 users.id>
```

- `sub` 은 **포털의 users.id**, 곧 ID 토큰의 `sub` 다. 각 시스템이 자기
  `sso_subject` / `auth_sub` 로 들고 있는 그 값이다.
  포털 계정과 이어지지 않은 로컬 계정은 물을 수 없다(설계서 F-3) — 그 사람은
  자기 사이트의 알림만 보게 된다. 정상이다.
- 🔴 **비밀값을 주소에 싣지 마라.** `?client_secret=…` 이 붙어 오면 포털은
  400 으로 거절한다(그 값은 이미 접근 로그에 남았으니 **다시 발급**해야 한다).
- `client_id`·`client_secret` 은 포털이 그 시스템을 등록할 때 발급한 그것이다.
  새로 받을 것이 없다. 로그인(토큰 교환)에 쓰는 값과 **같은 값**이다.

## 답 (200)

```jsonc
{
  "items": [
    {
      "key": "rf-service-system:APPROVAL:123", // 목록 전체에서 유일 (client_id:id)
      "sourceId": "rf-service-system",         // 어느 시스템에서 왔는가
      "sourceName": "DSS A/S 관리 시스템",
      "id": "APPROVAL:123",
      "kind": "APPROVAL",
      "kindLabel": "결재 대기",
      "subject": "RF-2026-0007",
      "detail": "…",
      "href": "http://192.168.1.132:3000/repair-cases/123" // 🔴 절대 주소, 손대지 마라
    }
  ],
  "count": 3,          // 배지 숫자. 각 시스템이 센 값의 합
  "sources": [         // 어디에 물었고 어디가 빠졌는가
    { "clientId": "rf-service-system", "name": "DSS A/S 관리 시스템", "ok": true, "count": 3 }
  ],
  "degraded": false,   // 🔴 한 곳이라도 못 물어봤는가. 빈 목록과 다른 말이다
  "dismissed": [       // 🔴 그 사람이 ✕ 로 지운 알림의 열쇠 — **부른 사이트 몫만**
    "rf-service-system:APPROVAL:456"
  ],
  "acknowledged": [    // 🔴 그 사람이 ✓ 로 확인한 알림의 열쇠 — **부른 사이트 몫만**
    "rf-service-system:STOCK_SHORTAGE"
  ]
}
```

`items` 는 `@dss/ui` 의 `NotificationBellItem` 과 **글자 하나까지 같은 모양**이다.
받은 배열을 종에 그대로 넘기면 된다. `kind`·`kindLabel`·`detail` 은 없으면 빈
문자열로 온다(`null` 이 아니다).

## 🔴 `dismissed` — 사이트가 **제 알림 목록에서 빼야 하는** 열쇠

사람이 종에서 ✕ 를 누르면 그 기록은 **포털에** 쌓인다(브라우저가 아니다 —
브라우저 저장소는 주소별로 갈려서 A/S 에서 지운 줄이 재고관리 종에 그대로
떴다). 그래서 어느 시스템에서 지우든 모든 시스템의 종에서 사라져야 한다.

- **남의 시스템 줄**은 포털이 **제 손으로 걸러서** 보낸다. `items` 에서 빠져
  있고 `count`·`sources[].count` 도 그만큼 줄어 있다. 사이트가 할 일이 없다.
- 🔴 **제 시스템 줄**은 포털이 손댈 수 없다. 애초에 포털이 안 보내는 목록이고
  (바로 아래 절), 사이트가 제 DB 에서 직접 계산해 이어 붙이는 것이기 때문이다.
  **그래서 `dismissed` 가 있다.**

```ts
const mine = await listMyNotifications(user);
const others = await fetchPortalFeed(user.ssoSubject);

// 🔴 이 한 줄이 없으면 「A/S 에서 지웠는데 A/S 종에만 그대로 뜬다」가 된다.
const dismissed = new Set(others.dismissed ?? []);
const myItems = mine.items.filter((row) => !dismissed.has(`${MY_CLIENT_ID}:${row.id}`));
```

- 열쇠 모양은 `items[].key` 와 **같다** — `{자기 client_id}:{id}`.
- 🔴 **개수도 함께 줄여야 한다.** 줄은 사라졌는데 배지 숫자가 그대로면 「알림이
  있다는데 열면 없다」가 된다. 0 아래로 내려가지 않게 한다(같은 대상을 한 번만
  세는 규칙이 있으면 뺀 줄 수가 개수보다 클 수 있다).
- 🔴 **그 사이트 몫만 온다.** 그 사람이 다른 시스템에서 지운 열쇠는 오지
  않는다 — 열쇠의 `id` 에는 수리 건 번호 같은 업무 식별자가 들어 있어서, 쓸
  일도 없는 남의 것을 보낼 까닭이 없다. 접두사로 골라낼 필요가 없다는 뜻이다.
- 지운 것이 없으면 **빈 배열**이 온다. 칸이 없어지는 일은 없다.
- 🔵 포털이 지움 기록을 못 읽으면 `dismissed` 가 빈 배열이고 `degraded` 가
  `true` 다. 그때는 지웠던 줄이 다시 뜬다 — **지움은 보기를 미루는 것이지
  지워지는 자료가 아니라서**, 종을 통째로 끄는 것보다 그 편이 낫다고 보았다.

🔵 **아직 안 고친 사이트도 그대로 돈다.** 모르는 칸은 JSON 을 읽는 쪽에서
조용히 무시되므로, 남의 줄은 포털이 걸러 주고 제 줄만 예전처럼 보인다. 일곱
사이트를 한 번에 고칠 필요가 없다.

### ✕ 를 눌렀을 때 보낼 곳

```
POST {포털}/api/integration/notification-dismissals
Authorization: Basic base64(urlencode(client_id) + ":" + urlencode(client_secret))
Content-Type: application/x-www-form-urlencoded

sub=<포털 users.id>&keys=<열쇠,열쇠,...>
```

읽기 통로와 **같은 자격증명·같은 거절**이다(아래 표). 열쇠는 `{client_id}:{id}`
모양이어야 하고, 모양이 틀리거나 모르는 시스템의 것은 **조용히 버려진다** —
한 줄 때문에 일괄 지우기가 통째로 실패하지 않는다. 한 번에 보낼 수 있는 수는
**200**이다(넘으면 400 `invalid_request`).

🔵 **몇 번을 다시 보내도 안전하다.** 같은 열쇠를 두 번 지우는 것은 한 번 지우는
것과 같다. 네트워크가 끊겨 답을 못 받았으면 그냥 다시 보내면 된다 — 포털이
이미 있는 열쇠를 조용히 넘긴다.

답(200): `{ "recorded": 2, "dropped": 0 }`. 🔴 `recorded` 는 **보낸 것 중 뜻이
지켜진 수**이지 표에 새로 생긴 행 수가 아니다 — 이미 지워져 있던 열쇠도 여기
센다. `dropped` 가 0 이 아니면 보내는 쪽의 열쇠 모양이 어긋났다는 뜻이다.

## 🔴 `acknowledged` — 사이트가 **제 알림 목록에서 빼야 하는** 확인(✓) 열쇠

`dismissed` 와 **쓰는 법은 같고 뜻이 다르다.** 2026-10-22 에 늘어난 칸이다.

```ts
const acknowledged = new Set(others.acknowledged ?? []);
const dismissed = new Set(others.dismissed ?? []);

const myItems = mine.items.filter((row) => {
  const key = `${MY_CLIENT_ID}:${row.id}`;
  return !dismissed.has(key) && !acknowledged.has(key);
});
```

- 🔴 **두 칸을 한 뭉치로 만들지 마라. 수명이 정반대다.**
  ✕ 지움은 「지금은 그만 보겠다」라 **로그아웃하면 돌아오고**, ✓ 확인은
  「해소됐다」라 **안 돌아온다.** 합쳐 두면 어느 쪽이 어느 쪽인지 알 수 없게 되고,
  확인을 지움으로 읽으면 로그아웃 뒤에 **안 돌아와야 할 줄이 돌아온다**(반대로
  지움을 확인으로 읽으면 **영구히 사라진다**).
- 🔴 **담기는 조건이 다르다.** 지움은 「지웠는가」 하나지만, 확인은 **셋이 모두**
  맞을 때만 담긴다 — 기록이 있고, **그때 본 내용과 지금 내용이 같고**, 포털
  관리자가 그 종류를 **「정보 확인용(`INFO`)」**으로 정해 두었을 때다. 판정은
  전부 포털이 한다(`src/lib/notifications/own-acknowledgements.ts`).
  - 🔵 그래서 재고관리의 **「한계수량 이하인 부품이 N종 더 있습니다」**처럼 id 가
    고정인 줄도 **3종이 10종이 되면 이 목록에서 빠져 다시 보인다.**
  - 🔵 **「승인용(`ACTION`)」 종류는 확인해도 여기 안 담긴다.** 기록은 남아 있고,
    관리자가 분류를 바꾸는 날부터 담기기 시작한다. 사이트는 고칠 것이 없다.
- 🔴 **사이트가 지문을 계산하지 않는다.** 내용이 바뀌었는지 보는 일은 포털이
  한다. 같은 규칙을 사이트마다 적으면 한 곳만 어긋나도 **그 시스템에서만 확인이
  영영 안 먹히고, 오류는 한 줄도 안 난다.**
- 🔴 **그 사이트 몫만 온다.** `dismissed` 와 같은 까닭이다.
- 뺄 것이 없으면 **빈 배열**이 온다. 칸이 없어지는 일은 없다.
- 🔵 포털이 확인 기록을 못 읽었거나 **그 사이트에 못 물어봤으면** `acknowledged`
  가 빈 배열이고 `degraded` 가 `true` 다. 그때는 확인해 둔 줄이 다시 뜬다 —
  **틀렸을 때 덜 나쁜 쪽**이기 때문이다. 「안 뺀다」가 틀리면 이미 처리한 알림이
  한 번 더 보이고, 「뺀다」가 틀리면 **아직 안 한 일이 안 보인다.**
- 🔴 **개수도 함께 줄여야 한다** — `dismissed` 와 같다.

### ✓ 를 눌렀을 때 보낼 곳

```
POST {포털}/api/integration/notification-acknowledgements
Authorization: Basic base64(urlencode(client_id) + ":" + urlencode(client_secret))
Content-Type: application/x-www-form-urlencoded

sub=<포털 users.id>&keys=<열쇠,열쇠,...>
```

지움 통로와 **같은 자격증명·같은 상한(200)·같은 거절**이다. 🔴 **지문 칸은 없다**
— 보내는 것은 열쇠뿐이고, 「그때 본 내용」은 포털이 제 목록에서 직접 계산한다.
답(200): `{ "recorded": 2, "dropped": 0, "skipped": 0 }`. `skipped` 는 **실패가
아니다**(그 줄이 포털 목록에 이미 없었다는 뜻이라 재시도하면 안 된다).

## 🔴 빠져 있는 것 — 부른 사이트 자신의 알림

포털은 **부른 사이트의 알림을 `items` 에 담지 않는다.** A/S 가 물으면 답에 A/S
알림이 없다.

까닭(자세히는 `src/lib/notifications/site-service.ts` 맨 위):

1. 자기가 이미 아는 것을 한 바퀴 돌아 받는 꼴이다(되돌기).
2. 🔴 포털은 30초 캐시를 든다. 자기 알림까지 거기서 받으면 **방금 처리한 일이
   30초 동안 종에 남는다** — 사람이 지금 일하고 있는 바로 그 시스템에서.
3. 포털이 죽어도 자기 알림은 그대로 보인다.

⚠️ **2026-10-22: 「담지 않는다」이지 「묻지 않는다」가 아니다.** 포털은 부른
사이트에게도 한 번 묻는데, 받아 온 줄은 **위 `acknowledged` 를 가리는 데만** 쓰고
`items`·`count`·`sources` 어디에도 넣지 않는다. 위 세 까닭은 그대로 지켜진다.
사이트가 받는 모양도 그대로다 — 칸이 하나 늘 뿐이다.

**그래서 사이트가 할 일:**

```ts
const mine = await listMyNotifications(user);   // 지금 하던 그대로
const others = await fetchPortalFeed(user.ssoSubject); // 이 통로

<NotificationBell
  items={[...mine.items, ...others.items]}
  count={mine.count + others.count}
/>
```

`mine` 을 위 아홉 칸으로 맞출 때 `key` 는 `자기 client_id + ":" + id`,
`sourceId` 는 자기 `client_id`, `href` 는 **절대 주소**로 만든다(포털에 내주는
`/api/integration/notifications` 가 이미 그렇게 만들고 있다 — 같은 함수를 쓰면
된다).

## 거절 (전부 `{ "error": …, "error_description": … }` · `cache-control: no-store`)

| 상태 | error | 언제 |
|---|---|---|
| 400 | `invalid_request` | `sub` 이 없다 · 너무 길다 · 🔴 비밀값이 주소에 실렸다 |
| 401 | `invalid_client` | 머리말이 없거나 깨졌다 · 없는 client_id · 시크릿이 틀리다 |
| 403 | `forbidden` | 🔴 그 사람이 없다 · 정지·대기 상태다 · **그 시스템에 들어갈 수 없는 사람이다** |
| 405 | — | POST 가 아니다 |
| 429 | `temporarily_unavailable` | 인증 실패가 잦다(정상 요청은 세지 않는다) |
| 503 | `temporarily_unavailable` | 포털이 DB 를 못 읽었다 |

403 셋은 **같은 본문**이다. 구분해 주면 사이트 하나가 묻는 것만으로 포털의
사용자 목록과 각자의 권한을 알아낼 수 있다.

🔴 **사이트는 거절을 삼켜야 한다.** 어떤 답이 와도 그 사이트의 화면은 떠야
한다. 포털이 죽거나 403 이 오면 **자기 알림만** 그리면 된다.

## 점검

```
npm run check:notify:site                                  # A/S 자격증명으로
SITE_ENV_FILE=../dss-improvements/.env.local npm run check:notify:site
```

거절 여섯 가지와 정상 왕복을 진짜 서버에 대고 확인한다. 자격증명은 사이트의
`.env.local`(`SSO_CLIENT_ID`·`SSO_CLIENT_SECRET`)에서 읽고 **찍지 않는다.**
