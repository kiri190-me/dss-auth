# 알림 지움을 포털에 모은다 — 설계안 (2026-10-19)

> 이 문서는 **구현 전 설계안**이다. 승인받은 뒤에 코드를 쓴다.
> 읽는 짝: `docs/사이트-알림-통로.md`(지금 있는 읽기 통로의 규격).

---

## 1. 왜 하는가

2026-10-19 에 A/S 관리 시스템의 알림 종에 **지우기**를 만들었다 — 줄마다 ✕, 바닥에
「보이는 알림 지우기 n건」. 지운 기록은 **브라우저**에 적고 **로그아웃하면 저절로 비워진다**.

🔴 **그런데 브라우저 저장소는 주소(포트)별로 갈린다.** A/S(3000)와 재고관리(3800)는 서로의
저장소를 못 본다. 그래서 **같은 사람이 시스템마다 다른 목록을 본다** —
A/S 에서 지운 줄이 재고관리 종에는 그대로 뜬다.

사용자 결정(2026-10-19):

> 「다른 시스템들에 붙은 전역 알림에도 이런 기능을 만들어줘. 그렇지 않으면 a/s시스템에
> 뜨는 알림과 다른 시스템에서 뜨는 알림의 내용이 달라지게 돼」

→ **포털 한 곳에 모아 적는다.** 어느 시스템에서 지우든 모든 시스템의 종에서 사라진다.

## 2. 지금 구조에서 알아 둘 것

### 2-1. 알림은 아무 데도 쌓이지 않는다

각 시스템이 **매 요청마다 업무 자료에서 다시 계산**한다. 포털도 알림을 저장하지 않는다.

🔵 **이 설계가 그 원칙을 깨지 않는다.** 포털에 쌓는 것은 **열쇠 문자열뿐**이고
알림 본문은 여전히 매 요청 계산된다. 「알림을 저장한다」와 「사람이 지웠다는 뜻을 적는다」는
다른 일이다.

### 2-2. 포털이 모으는 길

```
A/S 종  ←①─  포털  ←②─  재고관리 · 개선요청 · 게시판 · 휴가
```

- ① `POST {포털}/api/integration/notifications` — 시스템이 포털에 묻는다.
  자격은 `Authorization: Basic base64(client_id:client_secret)`, 본문은 `sub={포털 users.id}`
- ② 포털이 각 시스템에 `GET {시스템}/api/integration/notifications` — 포털이 서명한 Bearer

🔴 **시스템이 포털에 물을 때 자기 자신은 목록에서 빠진다**(`exceptClientId`).
A/S 종은 「자기 것(직접 계산) + 포털이 준 남의 것」을 이어 붙인다.

### 2-3. 합치는 지점이 하나다

`src/lib/notifications/merge.ts` 의 `mergeSourceOutcomes()` 로 두 서비스가 수렴한다.
**거르는 자리를 한 곳에 둘 수 있다.**

### 2-4. 🔴 열쇠 모양이 한 곳만 다르다

| 어디 | 열쇠 |
|---|---|
| 포털이 만든 줄 | `{client_id}:{id}` |
| 재고관리 자기 줄 | `{sourceId}:{id}` — **이미 같은 모양** |
| 🔴 **A/S 자기 줄** | `{id}` — **접두사가 없다** |

A/S 가 자기 줄의 열쇠를 그대로 보내면 **포털이 어느 시스템 것인지 알 수 없다.**

### 2-5. 「로그아웃」은 이미 전역이다

시계는 셋이지만(포털 12시간 · A/S 8시간 · 재고관리 제 세션) **로그아웃은 한 번에 끊긴다** —
어느 시스템에서 로그아웃하든 포털로 가고, 포털이 백채널로 모든 시스템에 전파한다.

🔵 **그래서 「로그아웃하면 다시 뜬다」의 기준을 포털 로그아웃 하나로 잡을 수 있다.**

## 3. 설계

### 3-1. 포털에 표 하나 🔴 마이그레이션

```
notification_dismissals
  id               uuid     PK  default gen_random_uuid()
  user_id          uuid     NOT NULL  → users.id  ON DELETE CASCADE
  notification_key text     NOT NULL
  dismissed_at     timestamptz NOT NULL default now()

  UNIQUE (user_id, notification_key)
  INDEX  (user_id)
```

- `user_id` 는 **포털의 사람 번호**. 사람 행을 지우면 함께 사라진다
- `notification_key` 는 **`{client_id}:{id}` 모양**으로 통일한다(3-4 참조)
- 🔴 **수명 칸을 두지 않는다** — 로그아웃 때 행을 지우는 쪽이 단순하다(3-6)

**마이그레이션 번호**: 포털의 지금 최신이 `0004` 이므로 **`0005`**.
🔴 표를 새로 만드는 마이그레이션은 `0000` 이후 처음이다.

### 3-2. 거르는 자리 — 🔴 캐시 **바깥**

포털에는 두 캐시가 있다(30초):

| 캐시 | 열쇠 |
|---|---|
| `feedCache` | `userId` |
| `siteFeedCache` | `{clientId}:{userId}` |

🔴 **거른 결과를 캐시하면 「지웠는데 30초 남는다」가 된다.** 그리고 `siteFeedCache` 는
열쇠에 `clientId` 가 섞여 있어 사람 하나를 버리려면 등록된 시스템을 전부 돌아야 한다.

**→ 거르지 않은 feed 를 지금처럼 캐시하고, 꺼낸 뒤 응답을 만들기 직전에 거른다.**
지움 목록은 매 요청 DB 에서 새로 읽는다(사람 한 명치, 색인 하나).
🔵 캐시 무효화가 **아예 필요 없어진다**. ✕ 를 누른 **다음 화면부터 바로** 사라진다.

### 3-3. 숫자도 함께 줄인다

`PortalNotificationFeed` 에는 숫자가 두 군데 걸려 있다:
- `feed.count` — 배지
- `feed.sources[].count` — `/apps` 타일의 빨간 점이 이것을 본다

🔴 **지운 줄 수만큼 빼되 0 아래로 내려가지 않게 한다.** 저쪽이 센 규칙(한 대상 한 번)을
포털이 모르므로 정확하지 않을 수 있다 — A/S 가 이미 같은 처리를 하고 있다.

### 3-4. 응답에 한 칸 — 🔴 왕복이 안 는다

`POST /api/integration/notifications` 의 응답에 **`dismissed: string[]`** 을 더한다.

- **남의 줄**: 포털이 제 손으로 걸러 `items`·`count` 를 줄여 보낸다. 시스템은 아무것도 안 한다
- **자기 줄**: 포털이 `dismissed` 를 그대로 돌려주고, 시스템이 **제 접두사가 붙은 것만** 골라
  자기 목록에서 거른다

🔵 A/S 의 `normalizePortalNotificationFeed` 가 **모르는 칸을 조용히 버린다** —
**포털이 먼저 배포돼도 A/S 는 안 깨진다.**

### 3-5. 새 쓰기 통로

```
POST {포털}/api/integration/notification-dismissals
Authorization: Basic base64(urlencode(client_id) + ":" + urlencode(client_secret))
Content-Type: application/x-www-form-urlencoded

sub=<포털 users.id>&keys=<열쇠,열쇠,...>
```

🔴 **기존 읽기 통로의 문 여섯을 순서까지 그대로 베낀다**(`site-feed.ts`):

1. 주소에 비밀값이 실려 있는가 → 400 `invalid_request`
2. `Authorization: Basic` 이 읽히는가 → 401 `invalid_client`
3. 본문에 `sub` 이 있는가 → 400
4. `findActiveClient` + `verifySecret` → 401
5. `findUser`, `status === "ACTIVE"` → 403 `forbidden`
6. 🔴 `hasAccess(subject, client)` → 403 `forbidden`

거절 본문·머리말·`429`·`cache-control: no-store` 도 그대로.

**추가로 이 통로만의 문 둘:**

7. 🔴 **열쇠 개수 상한** — 한 번에 받을 수 있는 수를 정한다(예: 200).
   일괄 지우기가 한 번에 보내는 양을 덮으면서, 표가 폭주하지 않게 한다
8. 🔴 **열쇠 모양 검사** — `{client_id}:{id}` 이고 `client_id` 가 **등록된 시스템**인가.
   모양이 틀린 것은 조용히 버린다(전체를 거절하지 않는다 — 한 줄 때문에 일괄이 통째로
   실패하면 사람이 할 수 있는 일이 없다)

### 3-6. 로그아웃 때 비운다

포털의 `api/oidc/logout` 에서 **그 사람의 지움 기록을 지운다**(`DELETE WHERE user_id = ?`).
그 자리에 사람 번호가 이미 손에 있다.

🔴 **덮지 못하는 경우 하나**: 로그아웃을 안 누르고 세션이 **만료로** 끝나면 아무 훅도 안 돈다.
→ **보관 기간으로 덮는다**. 포털에 이미 `npm run db:purge`(만료 정리 스크립트)가 있으므로
`dismissed_at` 이 **하루** 넘은 행을 지우는 한 줄을 더한다.
🔵 포털 세션이 12시간 절대 만료이므로 하루면 넉넉하다.

## 4. 🔴 A/S 열쇠에 접두사 붙이기

A/S 자기 줄의 열쇠에 **`rf-service-system:`** 을 붙여 포털에 보낸다.
(재고관리는 이미 붙여서 만들고 있어 고칠 것이 없다.)

🔴 **그 순간 지금 브라우저에 쌓인 지움 기록이 전부 무효가 된다.**
→ A/S 의 저장소 열쇠 접두사(`dss.notifications.dismissed.v1.`)의 **`v1` 을 `v2` 로 올려**
옛 기록을 조용히 버린다. 그 장치가 이미 마련돼 있다.

## 5. 🔴 치르는 값 셋 — 사용자에게 알린 것

### ① 포털 DB 에 표가 생긴다
그 서버는 **운영에서 일곱 사이트의 로그인을 떠받친다.** 마이그레이션을 거기에 돌린다는 뜻이다.
→ 배포 절차를 6절에 적는다.

### ② 지운 줄이 한 박자 늦게 사라진다
지금은 브라우저라 즉시인데, 서버로 옮기면 **포털 응답이 도착한 뒤** 사라진다.
A/S 는 포털 응답을 **기다리지 않고** 화면을 그리기 때문이다(모든 화면이 포털 왕복만큼
느려지지 않게 일부러 그렇게 해 두었다).

🔵 **완화**: ✕ 를 누른 **그 순간**은 화면에서 바로 숨긴다(지금도 그런 상태 관리가 있다).
어긋나는 것은 **새로고침 직후**뿐이고, 그때 한 박자 뒤 사라진다.

### ③ 새 쓰기 통로에 사칭 위험이 붙는다
지금 통로는 시스템이 `sub` 에 **누구 것인지 스스로 적어 보내는** 구조다.
읽기에서 새는 것은 「남의 밀린 일 건수」지만, **쓰기에서는 「그 시스템을 쓸 수 있는 아무
사람의 알림이나 숨길 수 있다」**가 된다.

🔵 **완화**: ⑥ `hasAccess` 문이 그대로 걸리므로 **그 시스템에 권한이 있는 사람**에 한정된다.
그리고 숨기는 것은 **하루 안에 저절로 돌아온다**(로그아웃 또는 보관 기간).
지워지는 자료가 아니라 **보기를 미루는 것**이다.

## 6. 고칠 곳과 배포 순서

### 고칠 곳

🔴 **종을 쓰는 사이트는 일곱이다**(실측 2026-10-19). 그런데 **알림을 내는 곳은 다섯**이다 —
계측기·PO 는 **제 알림이 없고 남의 알림만 본다**. 그래서 고칠 양이 두 갈래로 갈린다.

| 저장소 | 몇 군데 | 무엇 |
|---|---|---|
| **포털** | 5 | 표(마이그레이션 0005) · 거르는 순수 함수 · 두 서비스의 응답 · 새 쓰기 통로 · 로그아웃 정리(+purge 한 줄) |
| **A/S** | 3 | 열쇠 접두사(+`v2`) · 브라우저 대신 서버 답을 쓰기 · ✕ 에서 포털로 POST |
| **재고관리 · 개선요청 · 게시판 · 휴가** | 각 2~3 | 제 줄 열쇠 확인(이미 접두사를 붙이는 곳도 있다) · 포털 답으로 거르기 · ✕ 배선 |
| **계측기 · PO** | 각 2 | 🔵 **제 알림이 없어 접두사 일이 없다.** 포털 답으로 거르기 · ✕ 배선만 |
| **공용 묶음** | **0** | ✕ 단추는 이미 들어가 있다 |

🔵 **포털이 걸러 주므로 사이트 쪽 일이 작다** — 남의 줄은 애초에 안 오고, 사이트는
✕ 를 포털로 넘기기만 하면 된다. 🔴 **자기 줄을 거르는 일은 알림을 내는 다섯에만 있다.**

### 🔴 배포 순서

```
1. 포털  — 표 + 거르기 + 응답 칸 + 쓰기 통로
2. A/S · 재고관리 — 아무 순서나
```

🔵 **포털이 먼저 나가야 한다.** 시스템들이 모르는 칸을 조용히 버리므로 **포털만 나가 있어도
아무것도 안 깨진다**(지움이 아직 안 쓰일 뿐). 반대로 시스템이 먼저 나가면 **지웠는데
포털이 못 받는** 상태가 된다.

🔴 **포털 마이그레이션은 별도 승인을 받고 돌린다.** 운영 DB 백업을 먼저 뜬다.

## 7. 시험 계획

🔵 **포털의 알림 시험은 DB 를 하나도 안 쓴다** — `site-feed.ts` 가 DB 조회 넷을 전부
인자로 받고, `gather.ts` 는 `fetchImpl` 을 받는다. **새 통로도 같은 모양으로 지어야**
시험이 붙는다.

| 무엇을 지키나 | 어디서 |
|---|---|
| 거르기가 `items`·`count`·`sources[].count` 를 **함께** 줄인다 | 포털 순수 시험 |
| 숫자가 0 아래로 안 내려간다 | 포털 순수 시험 |
| 🔴 문 여섯 + 추가 둘이 **순서까지** 기존 통로와 같다 | 포털 순수 시험 |
| 모양이 틀린 열쇠 하나가 **일괄 전체를 거절시키지 않는다** | 포털 순수 시험 |
| 🔴 응답에 `dismissed` 가 없어도 A/S 가 안 깨진다 | A/S 순수 시험 |
| 🔴 A/S 가 자기 줄에 접두사를 붙여 보낸다 | A/S 소스 시험 |
| 🔴 로그아웃이 그 사람 기록을 **그 사람 것만** 지운다 | 포털 통합 시험(DB) |

🔴 `service.ts`·`site-service.ts` 는 `server-only` 라 **시험이 없다** — 거르는 일을
**순수 함수로 빼야** 덮인다.

## 8. 정해진 것과 안 정한 것

### 🔵 정해진 것 (2026-10-19 사용자)

- **종이 있는 일곱 사이트 전부에 ✕ 를 단다** — 계측기·PO 도 포함.
  그 둘은 제 알림이 없지만 **남의 알림을 보므로** 거기서도 지울 수 있어야 한다.
- **사칭 위험을 받아들인다**(5절 ③) — 기존 통로와 같은 문을 쓰고, 숨기는 것은 하루 안에
  돌아온다. **지워지는 자료가 아니라 보기를 미루는 것**이다.

### 아직 안 정한 것

1. **열쇠 개수 상한의 값** — 200 을 제안한다(포털이 시스템당 200줄에서 자르므로).
2. **보관 기간** — 하루를 제안한다(포털 세션 12시간).
3. **포털 제 화면의 종** — 포털에는 알림 종이 **없다**(`/apps` 타일의 빨간 점뿐).
   지우는 행동은 언제나 위성 시스템에서 일어난다. 나중에 포털에 종이 생기면 그때 ✕ 를 단다.
4. **어느 사이트부터 할 것인가** — 포털을 먼저 배포한 뒤 사이트는 하나씩 따라가도 된다.
   🔵 **아직 안 고친 사이트는 지금 그대로 돈다** — 남의 줄만 포털이 걸러 주고, 제 줄은
   예전처럼 보인다. 한 번에 일곱을 다 할 필요가 없다.

## 9. 되돌리기

- **포털 표**는 값을 더하기만 하므로 지워도 자료가 안 없어진다(`DROP TABLE`).
- **A/S·재고관리**는 커밋을 되돌리면 브라우저 저장 방식으로 돌아간다.
- 🔴 다만 **응답의 `dismissed` 칸을 없애면** 그 칸을 읽도록 바뀐 시스템이 **지움을 영영
  못 받는다**(깨지지는 않는다 — 빈 목록으로 읽힌다). 포털을 먼저 되돌리지 말 것.
