# 주소 — IP가 바뀌어도 로그인이 살아 있게

## 무엇이 문제였나

통합 로그인은 **주소를 문자 단위로 대조**한다. 와일드카드도 정규화도 없다
(그 이유는 `src/lib/oidc/redirect-uri.ts`). 그래서 개발 PC의 IP가 바뀌면
등록된 값이 전부 어긋나 로그인이 통째로 막힌다.

문제는 고칠 곳이 흩어져 있었다는 점이다. 시스템 하나당 네 곳, 시스템이
넷이면 열세 곳 + 카카오 콘솔. 하나만 빠뜨려도 증상은 **"로그인이 안 된다"
하나**로 뭉뚱그려져 원인을 가리키지 않는다.

실제로 A/S 시스템 `next.config.ts`의 주석에는 이 목록이 **하루에만 세 번**
늘어난 기록이 남아 있다(192.168.1.132 → 192.168.35.215 → 192.168.0.12 →
핫스팟 10.150.71.135).

## 지금은 어떻게 되나

주소를 **적지 않는다.** 두 가지 장치를 쓴다.

### 1. 설정값의 `auto`

```
OIDC_ISSUER=auto          # → http://<이 기계의 사내망 IPv4>:3100
OIDC_ISSUER=auto:3200     # 포트를 지정하고 싶을 때
```

실행 시점에 `os.networkInterfaces()`를 읽어 이 기계의 사내망 IPv4를 고른다.
판정 규칙은 `src/lib/config/lan-address.ts`에 있고 테스트로 고정돼 있다.

- 루프백(127.0.0.1)과 링크로컬(169.254/16)은 제외한다
- 가상 어댑터(WSL·Hyper-V·VMware·Docker…)는 뒤로 민다 — WSL도 사설 대역을
  들고 있어 주소만으로는 진짜 랜카드와 구별되지 않는다
- 그래도 남으면 192.168 → 10 → 172.16~31 순으로 고른다
- 하나도 못 찾으면 **조용히 localhost로 물러서지 않고 멈춘다.** 그 상태로
  뜨면 폰에서 들어온 로그인이 "성공했는데 돌아오지 못하는" 가장 설명하기
  어려운 모양으로 깨진다

같은 판정이 A/S 시스템·계측기 시스템·dss-home에도 복제돼 있다. 저장소가
서로를 참조하지 않아 공유 패키지가 없기 때문이다. **한쪽 규칙을 고치면
나머지도 고쳐야 한다** — 둘이 서로 다른 주소를 고르면 redirect_uri가
어긋난다.

### 2. 등록 주소의 `{lan}`

DB에 등록하는 주소의 호스트 자리에 쓴다.

```
http://{lan}:3000/api/auth/sso/callback
```

비교 **직전에** 포털이 자기 기계의 실제 주소로 펼친 뒤, 평소와 똑같이 정확
일치로 대조한다. **와일드카드가 아니다:**

1. 펼쳐진 값은 언제나 이 기계의 주소다. 출처가 `os.networkInterfaces()`라
   요청하는 쪽이 그 목록을 바꿀 수 없다
2. 펼친 뒤의 비교는 손대지 않았다 — 여전히 `candidate === requested`
3. 주소를 못 찾으면 목록이 비어 **아무것도 통과하지 못한다.** 느슨해지는
   쪽이 아니라 막히는 쪽으로 실패한다

등록할 때는 셸이 중괄호를 건드리지 않도록 작은따옴표로 감싼다:

```bash
npm run client:register -- --client-id rf-service-system \
    --redirect-uri 'http://{lan}:3000/api/auth/sso/callback'
```

## 지금 상태 보기

```bash
npm run net:doctor
```

이 기계가 가진 주소, `auto`가 무엇으로 풀렸는지, 등록된 주소가 무엇으로
펼쳐지는지, 그리고 **카카오 콘솔에 넣어야 할 값**을 한 화면에 보여준다.
자리표시자를 쓰지 않아 주소가 굳어 있는 등록값이 있으면 ⚠️로 짚어준다.

## 카카오만은 자동이 안 된다

카카오 개발자 콘솔의 Redirect URI는 우리가 바꿀 수 없다. IP가 바뀌면
**카카오 로그인만 따로** 깨진다 — 다른 수단은 멀쩡해서 더 헷갈린다.

그래서 주소를 아예 고정해 두는 편이 낫다.

### 주소 고정 (공유기 DHCP 예약)

먼저 이 PC의 MAC 주소와 공유기 주소를 확인한다. 값을 여기 적어 두지 않는
이유는 이 저장소가 **공개**이기 때문이다 — MAC 주소는 바뀌지 않는 기기
식별자라 굳이 밖에 내놓을 이유가 없다.

```powershell
# 랜/Wi-Fi 어댑터의 MAC
Get-NetAdapter | Where-Object Status -eq Up | Select-Object Name, MacAddress

# 공유기(기본 게이트웨이) 주소
(Get-NetRoute -DestinationPrefix '0.0.0.0/0' | Select-Object -First 1).NextHop
```

현재 IP는 `npm run net:doctor`가 대표 주소로 알려준다.

ipTIME 기준 절차(펌웨어에 따라 메뉴 이름이 조금 다르다):

1. 브라우저로 위에서 확인한 공유기 주소 접속 → 관리도구
2. **고급 설정 → 네트워크 관리 → DHCP 서버 설정**
3. 아래 "사용 중인 IP 주소 정보"에서 그 MAC을 가진 항목을 찾는다
4. 그 항목을 골라 **수동 주소 입력(고정 IP 할당)** 으로 등록한다
5. 등록한 주소를 DHCP 자동 할당 범위 **밖**으로 잡으면 더 안전하다

고정한 뒤 카카오 콘솔에 `http://<고정한 주소>:3100/api/kakao/callback`을
한 번 등록하면 끝난다.

> 핫스팟처럼 고정할 수 없는 환경이라면 카카오는 PC 브라우저
> (`http://localhost:3100`)로만 쓰고, 폰 테스트는 카카오 없이 한다.

## ⚠️ 컨테이너 안에서는 `auto`가 통하지 않는다

`auto`와 `{lan}`은 `os.networkInterfaces()`를 읽는다. **브리지 네트워크로 띄운
컨테이너 안에서 그것은 NAS의 사내망 주소가 아니라 컨테이너의 주소**
(172.17.x.x 같은 값)다.

그대로 두면 발급되는 ID 토큰의 `iss`가 아무도 닿을 수 없는 주소가 되고,
redirect_uri는 어느 것과도 일치하지 않는다. 증상은 여느 때처럼 "로그인이
안 된다" 하나뿐이라 원인을 가리키지 않는다.

이 저장소에는 이미 `Dockerfile`과 `docker-compose.yml`이 있으므로, 컨테이너로
띄우는 순간 해당된다. 셋 중 하나를 고른다:

| 방식 | 설정 |
|---|---|
| 리버스 프록시 뒤 도메인 (권장) | `OIDC_ISSUER=https://<도메인>`을 직접 적고 등록값도 그 도메인으로 |
| 사내망 IP로 계속 운영 | NAS의 고정 IP를 직접 적는다 (`auto`를 쓰지 않는다) |
| host 네트워크로 띄움 | `auto`가 그대로 동작한다. 대신 포트 충돌을 직접 관리해야 한다 |

`npm run net:doctor`를 컨테이너 안에서 실행하면 무엇이 잡히는지 바로 보인다.

## HTTPS로 옮길 때 되돌릴 것

`auto`는 언제나 `http`를 만든다. 리버스 프록시를 세워 도메인으로 서비스하는
단계에서는 **`auto`가 아니라 그 도메인을 직접 적는다** — 밖에서 보이는
이름은 이 기계가 알아낼 수 있는 값이 아니다. 같은 시점에
`OIDC_ALLOW_HTTP_REDIRECT_URIS`도 `false`로 되돌린다
(`src/lib/config/transport-check.ts`가 이 조합을 검사한다).

NAS로 옮기는 절차는 `../dss-deploy/runbook/`에 있다.
